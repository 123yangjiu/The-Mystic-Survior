## 二、项目描述（一段话版，自我介绍时用）

> 这是我独立开发的 2D Roguelite 生存游戏，用 Godot 4.7 + GDScript 从零实现，约 4700 行代码，
> 已发布到 TapTap，支持 Windows / macOS / Android。
> 战斗上做了自动攻击 + 走位 + 升级构筑；架构上把敌人拆成 25 个可复用组件，
> 把数值和内容全部放进 Resource 资源配置，新增一种敌人只需要摆组件 + 填一条数据。
> 局内刷怪节奏是自适应的：难度按指数曲线收紧，同时用场上敌人总血量反向调节刷新间隔。
> 后期还做了一轮测量驱动的性能优化，把高频飘字的创建开销降低了 73%。

## 三、简历条目（挑 4~5 条，按岗位侧重）

**① 组件化敌人架构（架构 / 客户端岗最值钱）**

> 设计并实现组件化敌人系统：以 `EnemyComponent` 基类自动注册到 `Enemy.all_component` 登记表，
> 配合 `AreaInComponent` 区域反查机制解耦伤害判定，用 **25 个可复用组件**支撑起 **14 种敌人**
> 与 6 种特殊刷怪事件；新增敌人的成本从"写一套脚本"降为"摆组件 + 填一条数据资源"。

**② 全局信号总线 + 暂停引用计数（解耦能力）**

> 基于自动加载单例实现全局事件总线（14 个跨模块信号）与整局状态管理，
> 用**暂停引用计数**统一处理升级选卡、设置、结算三处并发暂停，
> 消除了"关闭一个界面把另一个界面的暂停也解除"的状态竞争问题。

**③ 数据驱动的内容管线（工具 / 玩法岗）**

> 将 27 张升级卡与 14 条敌人配置全部改为 Godot Resource（`.tres`）驱动，
> 把"解锁型 / 只能拿一次 / 与其他卡互斥 / 出现难度区间"等规则**字段化**，
> 平衡性调整与内容扩展无需改动代码。

**④ 自适应刷怪节奏（玩法 / 数值）**

> 刷怪间隔按难度指数曲线 `base·e^(-decay·difficulty)` 收紧，
> 并每 2 秒根据场上敌人总血量与目标血量做 `clamp(0.2, 1.5)` 的反向调节，
> 配合"离屏回收 + 出生保护"，避免后期"怪堆成墙"或前中期"空场没事干"。

**⑤ 升级构筑系统（分层抽取 / 稀有度控制）**

> 升级三选一采用分层抽取：主池去重 → 同一张卡第二次被选中后转入"神秘池"（2% 概率再现）→
> 次数上限出池；配合 `self_lock` 互斥锁（三把进阶枪只能选一把），
> 保证构筑组合不冲突、不早熟，候选张数还会随挑战模式动态调整。

**⑥ 测量驱动的性能优化（性能 / 工程岗）**

> 用离屏微基准定位高频对象的真实开销：飘字单次创建 48.4µs，其中 `instantiate` 占 35µs；
> 据此引入**飘字对象池**（池挂在图层节点上、随场景销毁），单次开销降至 **13.1µs（-73%）**，
> 实测复用率 76%；同时去掉每只敌人一个 `Timer` 节点（-4.7µs/只，-1 节点/只）。
> 对分组查找（实测 0.089µs）等非瓶颈项**明确不改**，避免无收益的复杂度。

**⑦ 移动端适配（如果投的是手游方向）**

> 自研多点触控虚拟摇杆（finger id 跟踪、浮动/固定双模式），
> 640×360 逻辑分辨率 + 整数缩放 + 最近邻采样保证像素画面不糊，
> 桌面与触屏共用同一套"方向 → 向量"输入抽象，一套代码覆盖 Windows / macOS / Android。

> 💡 建议：**架构类 ① + ②，性能类 ⑥，玩法类 ④ 或 ⑤，再按岗位加一条**。
> 七条全上反而像堆砌。

## 四、面试可能被追问（答案都在仓库里）

| 问题 | 一句话回答 |
| --- | --- |
| 组件怎么知道属于哪个敌人？ | 组件在 `_ready` 里找 `owner`（不是 Enemy 就往上找父节点），等 owner ready 后登记进 `Enemy.all_component` |
| 为什么要有 `AreaInComponent` 中间层？ | 物理回调里只有 Area2D，没有"它属于谁"的信息；套一层后用 `return_component()` 沿父链反查，避免在编辑器里手连一堆 NodePath |
| 敌人数据改了要改代码吗？ | 不用，`EnemyUnlockEntry`（`.tres`）里有解锁难度、消失难度、权重、血量，管理器只读数据 |
| 刷怪节奏为什么能自适应？ | 每 2 秒统计场上敌人 `max_health` 总和，与"目标血量"（按难度和权重估算）比，用 `clamp(0.2,1.5)` 缩放基础间隔 |
| 神秘池为什么存在？ | 防止"同一张卡无限叠"导致 build 过早固定；第二次选到后转入低频池，保留可能性但大幅降概率 |
| 暂停为什么用计数器？ | 升级、设置、结算可能同时暂停，布尔会被任一处提前恢复；计数减到 0 才真正 `paused=false` |
| 对象池为什么只做了飘字？ | 实测飘字创建 48.4µs 且频率最高；子弹 14-28µs 但频率低、每个能力复位逻辑不同，风险大于收益 |
| 优化后帧率提升多少？ | 没有提升——本机已被 vsync 封顶（240Hz，帧间隔 4.17ms）；收益是降低分配抖动与高峰期的帧时间尖刺 |
| 怎么证明优化有效？ | 离屏微基准（`--headless`、200 次平均），单次 48.4µs → 13.1µs；游戏内 20 秒高压战斗复用率 76% |
| 为什么不用 ECS？ | 每个组件是场景树里的真实节点，能直接复用编辑器和物理系统；这个体量下 ECS 的数据搬运成本换不来收益 |

## 五、措辞红黑榜

| ❌ 别写 | ✅ 换成 |
| --- | --- |
| 对象池优化，同屏 200+ 敌人稳定 60fps | 针对高频飘字引入对象池，单次创建开销 48.4µs → 13.1µs（-73%） |
| 空间网格把 AI 从 O(n²) 降到 O(n) | （没做过，删掉）碰撞与伤害判定交给物理引擎宽相位 |
| 加权随机三选一 | 分层抽取 + 稀有度池 + 互斥锁的构筑系统 |
| 跨版本存档兼容 | 成就存档用 JSON + 递归合并默认值，兼容新增字段 |
| 用 ECS 架构 | 组件化节点架构（每个组件是真实节点） |
| 极致性能优化 | 测量驱动的针对性优化（并说明优化了什么、没优化什么） |

**通用原则**：写"**为什么**这么设计、**测出来**什么数"，不写"用了什么听起来厉害的名词"。
