# 10 · 性能优化记录

> 这一页记录"为什么要优化、怎么定位、改了什么、**测出来的数字**"，以及**哪些地方故意没改**。
> 所有数字都是在本机用 Godot 4.7 实测的（Windows / RTX 5060 Laptop / 240Hz），
> 测量脚本是一次性的，不进仓库。

---

## 一、先定位：别凭感觉优化

在动代码之前先做了两组微基准（离屏、`--headless`、200 次取平均）：

| 操作 | 单次耗时 |
| --- | ---: |
| `PackedScene.instantiate()`（飘字） | **35.19 µs** |
| `add_child()` | 0.71 µs |
| `start()`（2 个 Tween + 5 个属性动画） | 12.49 µs |
| `create_tween()` | 0.69 µs |
| `queue_free()`（只是标记，真正释放推迟到帧末） | 0.14 µs |
| 复用：改位置 + 显隐 | **0.64 µs** |
| `get_tree().get_first_node_in_group()` | 0.089 µs |
| `Timer.new()+add_child()+connect` | 4.73 µs |

结论很明确：

1. **飘字的大头是 `instantiate()`（35µs），不是动画（12µs）** —— 复用节点能省 70% 以上；
2. 分组查找只有 0.089µs，**根本不是瓶颈**，所以没有去"优化"它；
3. 每只敌人额外建一个 `Timer` 要 4.7µs，顺手可以去掉。

> 顺便记一个教训：一开始想直接在游戏里测"新建 vs 复用"，
> 结果两边都是 ~145µs —— 因为游戏本身有 100+ 敌人和物理在抢 CPU，测出来的全是噪声。
> **微基准要放到干净环境里跑**，游戏内只用来验证功能。

## 二、改动 1：飘字对象池（主要收益）

**问题**：战斗后期，每受到一次伤害就 `instantiate` 一个飘字、播完 `queue_free`。
一套 AoE 打到十几只怪，一帧就要建十几个节点。

**做法**（`script/ui/战斗/floating_text_pool.gd`）：

- 池子挂在"前景图层"节点自己的 **metadata** 上，而不是全局静态字典
  —— 切场景时池子跟着图层一起消失，不会留下指向已释放节点的野引用；
- `spawn()`：池里有就取出来重置（位置 / 缩放 / 透明 / 可见），没有才 `instantiate`；
- `recycle()`：飘字动画播完把自己藏起来放回池子（上限 96 个，超了才真销毁）；
- 飘字脚本 `floatingtext.gd` 从"播完 `queue_free`"改成"播完 `recycle`"，
  并保存两个 Tween 的引用，复用时先 `kill()` 旧动画。

**效果**：

| | 改之前 | 改之后 |
| --- | ---: | ---: |
| 单次弹出（含动画） | 48.4 µs | **13.1 µs** |
| 1000 次弹出合计 | 48.4 ms | **13.1 ms** |
| 每次弹出的堆分配 | 1 个节点 + 2 个 Tween | 0（复用） |

**实测复用率**：20 秒高压战斗里弹出 98 次，其中 74 次复用、只真正新建了 24 个节点（约 76% 复用）。

**改动的文件**：
`script/ui/战斗/floating_text_pool.gd`（新增）、
`script/ui/战斗/floatingtext.gd`、
`script/enemy_component/main_component/wound_component.gd`

## 三、改动 2：去掉每只敌人一个 Timer

**问题**：`Enemy._ready()` 里为了"出生 3 秒后标记为老怪"，
给**每只怪**都 `Timer.new() + add_child() + connect()`。
场上 100 只怪就是 100 个计时器节点、100 次信号连接。

**做法**（`script/enemy/main_enemy/enemy_xiaotrue.gd`）：

- `_ready()` 里只记一个出生时间戳 `_spawn_time`；
- `is_old` 改成**只读属性**，用时间戳现算：

```gdscript
var is_old:bool : get = _get_is_old
var _spawn_time:=0

func _get_is_old()->bool:
	return Time.get_ticks_msec()-_spawn_time>=new_time*1000.0
```

外部代码（`enemy_manager.check_health()` 里的 `if enemy.is_old`）**一行都不用改**。

**效果**：

| | 改之前 | 改之后 |
| --- | ---: | ---: |
| 每只怪生成时额外开销 | 4.73 µs | **0 µs** |
| 每只怪额外节点 | 1 个 Timer + 1 个信号连接 | **0** |

> 注意：这是**用墙上时间**算的老怪标记，而原来的 Timer 会跟着 `get_tree().paused` 一起暂停。
> 影响仅限于"暂停期间出生计时照走"，对"场外回收"这个用途可以忽略（已在代码注释里写明）。

## 四、故意没做的事（以及为什么）

| 想法 | 实测依据 | 结论 |
| --- | --- | --- |
| 把 `get_first_node_in_group` 缓存成变量 | 单次 **0.089 µs**，一次攻击最多调几次 | 收益 < 0.001ms，**不值得**改，改了反而多一份状态要维护 |
| 子弹 / 剑 / 火球做对象池 | `instantiate` 单次：剑 28.1 µs、火球 17.0 µs、子弹 14.1 µs；但**发射频率**远低于飘字 | 有收益，但每个能力场景的复位逻辑不同（信号、Tween、伤害配置），**风险大于收益**，暂不做 |
| 敌人做对象池 | 敌人场景 `instantiate` 单次 61.1 µs，但每只怪身上有 5~8 个组件节点和多个计时器 | 复位正确性极难保证，**不做** |
| 空间网格 / 邻居查询 | 敌人之间没有"谁离谁近"的逻辑，碰撞全交给物理引擎 | **不需要** |
| 敌人 `_process` 加速 | 每只敌人都加一个脚本回调，比原来的 Timer 更贵 | **不做** |

> 这一节比"做了什么"更重要：**能说清楚"为什么不做"，才说明是真的在做优化，而不是在堆技术名词。**

## 五、帧率为什么看不出差别

在本机做了前后各 20 秒的对比（同样抬高难度、同样种子、玩家锁血）：

| 指标 | 改之前 | 改之后 |
| --- | ---: | ---: |
| 帧间隔 p50 | 4.167 ms | 4.167 ms |
| 帧间隔 p95 | 6.944 ms | 4.545 ms |
| 场上敌人数 | 111 | 95 |

帧间隔 p50 都是 **4.167ms = 240Hz**，也就是**已经被 vsync 封顶**了。
这台机器跑这个体量的 2D 游戏本来就跑满，所以"帧率"根本反映不出差异 —— 这是正常的。

这类优化的真实收益在**低端机 / 移动端**：省掉的是每次弹出的堆分配和节点创建，
表现出来是"高峰期少一点掉帧/卡顿"，而不是"平均帧率提高"。

**所以对外表述要写成**：
"降低高频短生命周期对象的创建开销与内存分配抖动"，
而不是"帧率提升 XX%"。

## 六、怎么复现这套测量

微基准脚本（临时放 `dsh_bench.gd`，用 `--script` 跑，不进仓库）：

```gdscript
var t0 := Time.get_ticks_usec()
for i in 200:
	var node = scene.instantiate()
	t0 累计...
print("instantiate_us=", float(Time.get_ticks_usec() - t0) / 200)
```

要点：

1. **一定用 `--headless` 在干净环境跑**，游戏内测量会被其他系统的 CPU 抢占污染；
2. 每项至少 200 次取平均，第一次 `instantiate` 会包含类初始化，先热身一次；
3. `queue_free()` 只是标记，真正的释放发生在帧末 —— 想量它得跨帧；
4. 波动大就多跑几轮取中位数。

## 七、可以继续做的（按性价比排序）

| 优先级 | 事项 | 预期收益 | 风险 |
| :---: | --- | --- | --- |
| 1 | 子弹 / 剑做对象池（每类一个池） | 每次发射省 ~15-28 µs | 中（复位逻辑） |
| 2 | 飘字动画合成为一个 Tween | 每次省 ~0.7 µs | 低 |
| 3 | 受伤白闪也复用 Timer / 改成 `_process` | 每次受击省 ~1-2 µs | 低 |
| 4 | 敌人组件初始化延迟到首次需要 | 生成开销 | 中 |
