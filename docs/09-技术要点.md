## 三、真正的技术亮点（每条都给了代码位置）

### 1. 组件化敌人：新怪 = 摆组件 + 填一行数据

- **做法**：`EnemyComponent` 基类在 `_ready` 里**自动认领 owner**（`owner` 不是 Enemy 就往上找父节点），
  并把自己登记进 `Enemy.all_component`。所以敌人脚本里**不需要** `get_node` 一个个连子节点，
  任何组件想知道"我主人是谁""我主人在场吗"，从登记表里找就行。
- **胶水层**：所有伤害区/受伤区外面统一套一层 `Area2D + AreaInComponent`，
  碰撞发生时用 `return_component()` 沿父节点往上反查"这个区域属于哪个组件"，
  于是"谁打谁"变成一次组件查询，而不是靠节点路径硬连。
- **收益**：14 种敌人共享同一套组件；加新怪不改任何系统代码。
- **代码**：`script/class/enemy_component.gd`、`script/enemy_component/inside_scene/inside_collision.gd`、
  `script/enemy_component/main_component/*.gd`

> 面试展开点：为什么用"区域反查"而不是给每个组件导出一个 `Area2D`？
> —— 因为伤害判定要复用 Godot 物理引擎的宽相位，区域必须挂在场景树里；
> 而"这个区域是谁的"在编辑器里很容易连错，反查把关系变成**运行时推导**，少一份手连的配置。

### 2. 全局信号总线 + 暂停引用计数

- `GameEvent` 是自动加载单例（`script/gamevent.gd`），**14 个信号**把玩家、能力、刷怪、UI 解耦：
  吃瓶、升级、难度上涨、玩家死亡、胜利、特殊事件开关……互相不用知道对方存在。
- 它同时持有**整局的全局状态**：`difficulty`、`mode_index`、`paused`、`play_global_position`。
- **暂停用计数器而不是布尔**：升级选卡、设置界面、死亡结算**都可能同时暂停**，
  `stop_game()` 让 `paused+1`、`start()` 让 `paused-1`，只有减回 0 才真正 `get_tree().paused=false`。
  这避免了"关掉一个界面把另一个界面的暂停也解开"的经典 bug。
- **代码**：`script/gamevent.gd`、`script/文本及ui显示/upgrade/upgrade_screen.gd`、`die_screen.gd`

### 3. 数据驱动：数值和内容都在资源里

- 升级卡是 `AbilityUpgrade` 资源（27 个 `.tres`），敌人是 `EnemyUnlockEntry` 资源（14 条）。
- 卡片的"解锁型 / 只能拿一次 / 与其他卡互斥"全部是**字段**，不是 if 分支：
  `is_unlock`、`is_init`、`self_lock`、`lock_code`。
- 敌人配置里的 `unlock_difficulty` / `disapear_difficulty` / `weight` / `max_health` 直接决定
  它什么时候出现、多大概率出现、在刷怪节奏里占多少预算。
- **收益**：调平衡、加内容都不用碰代码；Resource 还能在编辑器里可视化编辑、被 `preload` 强类型引用。
- **代码**：`resource/ability_upgrade.gd`、`resource/enemy/enemy.gd`、`scene/大场景/game_event.tscn` 的 `upgrade_pool`

### 4. 刷怪节奏：指数难度曲线 + 场上血量反馈

这个项目的刷怪不是"固定间隔随机刷"，而是两层调节：

1. **随难度收紧**：`target_time = base_wait_time * exp(-decay * (difficulty-1))`，
   难度越高间隔越短，`decay` 还会按难度模式（普通 / 困难）微调。
2. **随场上压力反调**：每 2 秒统计一次场上所有敌人的 `max_health` 总和，
   和目标值（按当前难度与敌人权重估算）比一下：
   `normal_timer.wait_time = target_time * clamp(all_health / target_health, 0.2, 1.5)`。
   场上太肉就慢点刷，太干净就快点刷。

再加上 **离屏回收**（敌人存在超过 3 秒且跑出视口 80px 就 `queue_free`），
实现"怪多但不炸"的体感。
- **代码**：`script/manager/enemy_manager.gd` 的 `on_more_difficulty` / `_on_check_health_timeout` / `check_health`

> 面试提醒：这一条是**自适应节奏**，不是"性能优化"。被追问"那你怎么优化的"，
> 老实说"碰撞交给引擎、逻辑层只做 2 秒一次的统计、离屏回收"；对象池目前只在飘字上做了。

### 5. 能力系统的继承体系 + 运行时换枪

- 三层继承：`AbilityController`（冷却 / 伤害 / 数量 / 音量的通用逻辑）
  → `FlyAbilityController`（飞出去打人）→ `AK47AbilityController`（枪械）。
- 飞行物是 `FlyThing`（子弹、剑、火箭），原地造成伤害的是 `AgainstThing`（光环、圣光）。
- **换枪**：`AllGunAbilityController` 不继承不分支，而是**整颗替换子节点**，
  并把已累计的伤害 / 弹夹 / 射速加成写给新枪 —— 数据跟着玩家走，节点可以随便换。
- 所有能力都监听同一个信号 `GameEvent.ability_upgrade_add`，用 `match upgrade.ID` 决定自己怎么变强。
- **代码**：`script/class/ability_controller_class.gd`、`script/class/AK47_controller.gd`、
  `script/ability/controller/all_gun_ability_controller.gd`

### 6. 升级三选一：分层抽取 + 稀少度 + 互斥

不是简单的"从池子里抽 3 张"，而是四层规则叠起来：

| 规则 | 实现 |
| --- | --- |
| 主池抽取、每次不重复 | `can_chose_pool.pick_random()` + 本轮去重 |
| **神秘池**：同一张卡**第二次被选中后**就离开主池、转入神秘池，之后只有 **2%** 概率再出现 | `mystrious_pool` + `mystrious_probality = 0.02` |
| **次数上限**：神秘池也有上限，超过阈值彻底出池；"能力最大次数"挑战下阈值压到 2 | `limit_int` |
| **互斥锁**：`self_lock` 相同的卡只能拿一张（霰弹 / 狙击 / RPG 三张卡共用 `self_lock=2`，只能拿其中一把；基础 AK 不受限），`lock_code` 是反向解锁用的预留字段 | `add_upgrade()` |

- 卡片张数也会变：`randi_range(limit_number, 3)`，挑战模式下可能只给 2 张。
- **代码**：`script/manager/upgrademanager.gd`、`resource/upgrades/gun/get_*.tres`

### 7. 状态效果与"输入抽象"

- `StatusEffect` 基类：`attach_effect()` 时如果身上已经有同种效果就只**刷新时间**，否则挂上去；
  结束时 `recover_effect()` 复原。
- 有意思的是**混乱效果**：它不只是"打乱方向"，而是
  1. 洗牌 `InputMap` 里上下左右的按键事件（`action_erase_events` + `action_add_event`）；
  2. 同时改写虚拟摇杆的 `key_to_vector` 映射。
  也就是说**键盘和摇杆共用同一套"方向 → 向量"抽象**，一个效果同时作用于两种输入方式。
- **代码**：`script/status_effect/status_effect.gd`、`script/status_effect/effect_confusion.gd`、
  `scene/ui/虚拟摇杆2.gd`

### 8. 像素完美 + 移动端输入

- 逻辑分辨率 **640×360**，`stretch/mode=viewport`，窗口 1920×1080 整数放大；
  默认纹理过滤 Nearest、`snap_2d_transforms_to_pixel=true`，保证像素不糊、不抖。
- 虚拟摇杆自己处理 `InputEventScreenTouch / ScreenDrag`：
  **多点触控按 finger id 跟踪**、支持"浮动摇杆"和"固定摇杆"两种模式、摇杆偏移最大 22px 后归一化。
- 桌面端用 `pointing/emulate_touch_from_mouse` 让鼠标就能测手机操作。
- **代码**：`project.godot`、`scene/ui/虚拟摇杆2.gd`、`script/player.gd`

### 9. 场景切换与程序化特效（这次新做的）

- `ScreenFade` 把自己挂在 **root** 上而不是当前场景上，所以能撑过 `change_scene`，
  做出"淡出 → 换场景 → 淡入"（挂当前场景上的遮罩会跟着被销毁）。
- 传送门动画不写死美术序列：**1 张主立绘 + 1 张七帧收缩图 + 3 张粒子图**，
  配合运行时生成的径向渐变光晕、`GPUParticles2D` 加色混合、Tween + 正弦呼吸，
  参数全部 `@export`，改手感不用改代码。
- **代码**：`script/大场景/screen_fade.gd`、`script/场景互动件/portal.gd`、`scene/场景互动件/portal.tscn`

## 四、性能现状（老实说）

| 维度 | 现在的做法 | 评价 |
| --- | --- | --- |
| 碰撞 / 受伤判定 | 全部交给 Godot 物理引擎（`Area2D` + 层掩码），逻辑层**没有** O(n²) 遍历 | 合理，这也是不需要空间网格的原因 |
| 敌人目标位置 | `GameEvent.play_global_position` 全局坐标，每个敌人不用去查玩家节点 | 解耦且省一次查找 |
| 刷怪节奏统计 | 每 **2 秒**统计一次场上总血量（O(n)，n = 场上敌人数） | 频率低，开销可忽略 |
| 敌人回收 | 出场 3 秒后离开视口 80px 就 `queue_free` | 有效控制常驻数量 |
| 对象池 | 飘字已池化（单次 48.4µs → 13.1µs）；子弹、升级卡仍是即用即建 | 飘字是高频对象，先做收益最大的一个 |
| 每只敌人的额外节点 | 已把"出生 3 秒标记老怪"的 `Timer` 去掉，改时间戳现算 | 场上少 N 个计时器节点，每次生成省 4.7µs |
| 分组查找 | `get_first_node_in_group("前景图层")` 实测 **0.089µs/次** | 测过之后判定**不是瓶颈**，故意没改 |

## 五、性能优化：做了哪些、还没做哪些

> 完整过程与测量方法见 [10-性能优化记录](10-性能优化记录.md)。

| 项 | 状态 | 依据 |
| --- | :---: | --- |

## 六、拿来就能用的文案

> 更精简、可直接抄进简历的版本见 [11-简历技术要点](11-简历技术要点.md)。

### 项目简介（一句话）

> 独立开发的 2D Roguelite 生存游戏（Godot 4.7 / GDScript，约 4700 行），已发布至 TapTap，
> 支持 Windows / macOS / Android。

### 简历条目（挑 3~5 条）

1. **组件化敌人架构**：设计 25 个可复用行为组件与区域反查机制（`AreaInComponent`），
   把"写一套敌人脚本"变成"摆组件 + 填一条数据配置"，支撑 14 种敌人与 6 种特殊刷怪阵型。
2. **全局信号总线**：以自动加载单例统一 14 个跨模块事件与整局状态，
   并用**暂停引用计数**管理升级选卡、设置、结算三处并发暂停，消除暂停状态竞争。
3. **数据驱动内容管线**：27 张升级卡、14 条敌人配置全部走 Godot Resource（`.tres`），
   平衡性调整与内容扩展无需改动代码。
4. **自适应刷怪节奏**：刷怪间隔按难度指数曲线收紧，并每 2 秒根据场上敌人总血量与目标血量
   做 `clamp(0.2, 1.5)` 的反向调节，避免"怪堆成墙"或"空场没事干"。
5. **升级构筑系统**：主池 + 2% 神秘池 + 互斥锁 + 获取次数上限的分层抽取，
   保证组合不冲突、不出早熟 build，并按难度动态调整候选张数。
6. **测量驱动的性能优化**：用离屏微基准定位高频对象开销，为飘字引入对象池
   （单次创建 48.4µs → 13.1µs，-73%，复用率 76%），并去掉每只敌人一个 Timer 节点。
7. **移动端输入适配**：自研多点触控虚拟摇杆（浮动 / 固定双模式、finger id 跟踪），
   配合 640×360 逻辑分辨率 + 整数缩放 + 最近邻采样，桌面与触屏共用同一套输入抽象。

### 面试时最容易被追问的问题（提前准备）

| 问题 | 参考答案（都落在代码里） |
| --- | --- |
| 组件怎么知道自己属于哪个敌人？ | `EnemyComponent._ready()` 里先 `owner`、不是 Enemy 就往上找父节点，`await owner.ready` 后登记进 `Enemy.all_component` |
| 为什么要有 `AreaInComponent` 中间层？ | 让"伤害区/受伤区"能在物理回调里反查自己属于哪个组件，避免在编辑器里手连一堆 `NodePath` |
| 暂停为什么用计数器？ | 多个界面可同时暂停，布尔会被任一处恢复；计数减到 0 才解除 `get_tree().paused` |
| 为什么用 Resource 而不是 JSON 配表？ | 编辑器可视化编辑、强类型、可被 `preload` 直接引用、能存 PackedScene 引用 |
| 神秘池为什么不直接把卡删掉？ | 直接删掉会让 build 过早固定；改成低概率回池，保留"再来一次"的可能性 |
| ScreenFade 为什么要挂到 root？ | 切场景只销毁 `current_scene`，挂当前场景的遮罩会跟着消失，做不出连贯的淡入 |
| 敌人怎么"看"玩家？ | 统一读 `GameEvent.play_global_position`，避免每个敌人 `get_node` 玩家节点 |

## 七、不要写的话（防翻车）

| ❌ 不要写 | 原因 |
| --- | --- |
| "对象池优化，同屏 200+ 敌人稳定 60fps" | 只有飘字做了对象池（敌人/子弹没有），也没有测过帧率。要写就写"飘字对象池，单次 48.4µs → 13.1µs" |

| "用 ECS 架构" | 是组件化（每个组件是 Node），不是 ECS |

> 一句话：**能写的是"我这样设计是为了解决什么问题"，而不是"我用了什么听起来很厉害的技术"。**
